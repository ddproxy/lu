# Audit record

With `[audit] path` set, the controller appends a small JSON Lines record of job lifecycle events to that file. The record is off by default: without the table no file is opened, no lines are written and no audit work is performed. See [Configuration](config.md#audit) for the setting.

Each line is a self-contained JSON object with this shape:

```json
{"seq":4,"time":"2026-11-21T12:34:56.789Z","event":"started","job":"01ARZ3NDEKTSV4RRFFQ69G5FAV","node":"node-a","actor":"node-a","data":{"attempt":1,"epoch":9},"prev":"9a…","hash":"b3…"}
```

- `seq` is a 1-based sequence number that must increase by exactly one.
- `time` is UTC (RFC 3339, millisecond precision), generated by the controller.
- `event` is one of `submitted`, `leased`, `started`, `finished`, `failed`, `retried`, `cancelled`, `cordon_set`, `cordon_cleared`, `drain`, `collect_applied`, `scope_action`, `intake`, `draft_approved`, `draft_rejected`, `draft_expired` or `publish`.
- `job`, `node` and `actor` identify what changed: `actor` is the operator token name for operator actions and the node name for agent actions.
- `data` is a small object with an allow-list of scalar fields such as `attempt`, `epoch`, `outcome`, `class`, `provider`, `model`, `source`, `state`, `target`, `result`, `remote` and counts. **It never contains task text, prompts, artifact content or tokens.** Unsafe text values are dropped rather than truncated into the record.
- `prev` is the hex SHA-256 of the previous line's bytes; the first line uses 64 zeroes.
- `hash` is the hex SHA-256 of this line's canonical bytes with the `hash` field omitted.

`collect_applied` is recorded at submission when the job's collect mode applies diffs; it records that request, not proof that the agent later applied them. `cordon_set` covers retryable provider failures, and `cordon_cleared` covers explicit uncordon; automatic cordon expiry inside the store has no separate line. `publish` records each controller-side publish outcome with `target`, `result`, `remote` and `state`; `remote` is a configured name, never a URL or credential.

The writer holds the file open in append mode, creates it mode `0600` where supported, and calls `sync_data` after each line. On restart it reads and verifies the existing chain, then resumes it with the next sequence number and the last line's hash as `prev`.

## What verification proves

`lu audit verify <path>` walks every line: it checks the JSON shape and field order, the sequence, that `prev` equals the previous line's `hash`, and that `hash` equals SHA-256 of the line without `hash`. It reports the first break, or `ok: N record(s), head <hash>`.

Given a trusted copy of the last hash recorded elsewhere (see below), this gives a concrete guarantee:

> No later edit, insertion or deletion inside the file goes unnoticed.

Changing a byte of an existing line changes its hash and breaks that line and its successor. Inserting a line breaks the sequence or the `prev` link. Deleting a middle line breaks the `prev` link along with the hash mismatch; deleting trailing lines is caught by comparing the final head to the trusted hash. `verify --head <hash>` performs that comparison, and detects a truncated file even though every remaining line is internally consistent.

Pass `--json` to `lu audit verify` for machine-readable output (`ok`, `records`, `head`). `lu audit tail <path> [-n <lines>]` prints the last records, and `lu audit head <path>` prints the current head hash.

## What verification does not prove

- **It is unkeyed.** There is no secret or signature. Someone who can rewrite the whole file can recompute every hash and `prev` from the beginning and make a fully consistent forgery. The chain protects a file whose earlier contents (or at least its head hash) are kept somewhere the attacker cannot change.
- **It does not prove an event happened.** It proves the controller wrote a line with those fields. A compromised controller, agent reporting false completion, or a bug above the writer is outside the chain's scope.
- It is not a trusted timestamp: `time` is generated by the controller, so an attacker able to rewrite the whole file can also change times.
- It is not a database transaction with the job state. A write failure never rolls back or fails a job; a missing event is possible and is signalled only through the error counter and log.

## Anchoring the head

To make the guarantee hold, keep the head outside the file's trust boundary:

1. Print it with `lu audit head /var/log/lu/audit.jsonl` after a period of activity (or with `--json` for scripts), then store the hash in a place an attacker cannot rewrite: a ticket, configuration management record, WORM object or log host.
2. Later, run `lu audit verify /var/log/lu/audit.jsonl --head <trusted hash>`. Verification compares the trusted hash with the file's *final* head, so a clean run means the sealed file is byte-for-byte the one that produced that hash: no edits, insertions or deletions anywhere in it. Appending new lines changes the head and makes `--head` fail; use it for a rotated or frozen segment, or re-anchor after each period of writes.
3. Ship each line to an append-only log host as well. With a remote copy, compare the local chain to the remote one; a whole-file rewrite no longer suffices if the remote copy is protected. `lu audit tail` is useful for spot checks.

Record a new trusted head whenever you rotate or archive the file (or take a frozen copy of a still-growing file). For a live file, plain `lu audit verify` still detects internal tampering and can be rerun as the file grows, but without an anchor it cannot detect removal of trailing lines; the anchored check applies to a segment whose final head is known.

## Failure behaviour

Writing never blocks job processing. The controller sends events to the writer over a bounded channel (1024 records); when it is full, or a write fails, the event is dropped and:

- `lu_audit_write_errors_total` in `/metrics` is incremented (also reported as `audit_write_errors` by `lu status` and `lu show`);
- an error line is logged.

No job fails because of an audit error, and write errors are never silent. An operator should alert on the counter being non-zero. A startup open failure is different: it stops `lu serve` rather than silently running without the configured record.
