# FAQ

Short answers to the failures that come up most often. Each row links to the full explanation.

| Question | What it means | Check / action |
| --- | --- | --- |
| Why do I get `401` with the right token? | The bearer value did not match a configured hash for the route's scope. A correct-looking value still fails when an agent token is used on operator routes, when the stored hash was made from different bytes, when the controller hash is stale, or when the header has non-ASCII or control characters. Missing, unknown, malformed and wrong-scope tokens all return the same `401` with `WWW-Authenticate: Bearer`. | Use an operator token for `lu` and `lu mcp`. Compare file bytes and `token_sha256`: clients trim trailing CR/LF, but `sha256sum` hashes exact bytes. Restart the controller after changing its hash. See [tokens and TLS](tokens-and-tls.md#token-files-and-hashes). |
| Why is my job blocked forever? | One or more `after` dependencies are not `done`. `lu show` lists them as `after` rows; `(waiting)` marks the ones still unfinished, and a failed predecessor adds `blocked_reason: "predecessor failed"` with a `blocked_until` deadline. Dependents wait up to `[controller] blocked_dependent_ttl` (default 24h) before failing with class `dependency`; `include_failed` lets a dead dependency pass once the other dependencies are ready. | Run `lu show <id>`, then follow the chain with `lu show <dep-id>` and `lu graph <id>`. Retry the predecessor in place with `lu retry <dep-id>` (or `--chain` to restore blocked dependents transitively), or wait out the TTL. `lu retry` needs a terminal job. See [dependencies](dependencies.md#waiting-and-promotion) and [lifecycle](lifecycle.md#blocked-dependents-and-chain-bases). |
| Why did a dependency conflict fail the job? | The default `on_conflict = "fail"` stops before the harness. The job ends `failed` with `failure_class: "conflict"` and a summary like `input build (01AR...) could not be applied; conflicted files: src/main.rs`. Disagreeing chain bases can produce a summary naming two commits; opt-in `[stack]` policies resolve only covered paths. `conflict` never retries. | Read `lu show <id>`, `lu logs <id>` and the dependencies' `staged_commit` values. Fix the base, ref or patch; or resubmit with `lu submit --collect files`, `--on-conflict markers`, `--on-conflict skip`, or a narrowed `[stack]` policy path. After a chain finishes, merge its patch onto the moved branch yourself. See [dependencies](dependencies.md#one-base-per-chain) and [dependencies](dependencies.md#policy-paths-for-known-safe-conflicts). |
| Why does submit return `429`? | The controller throttles failed token checks per source address: ten failures in 60 seconds block that address for the rest of the window and return `429 rate_limited` with `Retry-After`. A successful request does not reset the count. Mirror syncs and base-pack fetches also return `429`: one sync at a time and six per operator per minute, or four base packs at a time and thirty per agent per minute. The MCP 30-submissions-per-minute cap is a tool `isError`, not HTTP 429. | Fix the token value, file and scope first. Wait the `Retry-After` seconds before retrying. See [security](security.md#tokens-scopes-and-hashes) and [mcp limits](mcp.md#limits-and-failures). |
| Why does a node never take work? | The queued job cannot be placed. The node may be offline, busy, draining, holding a `recovering` job, missing a required label, tainted without a matching tolerance, missing a healthy provider, or cordoned for the chosen provider. `lu nodes` has no `ONLINE` column. | Read `waiting` in `lu show <id>`, then `lu nodes --json`: check `online`, `draining`, `current_job`, `labels`, `taints`, `providers`, `provider_models` and `cordon_details`. Use `lu undrain <node>` if drained. See [dispatch](dispatch.md). |
| Why will a cordon not lift? | A cordon suppresses one `(node, provider)` pair. It expires on its timer, or a health-derived cordon clears after two consecutive healthy provider heartbeats; a non-healthy reading resets that streak. Boot recovery clears all cordons on controller restart. Use `lu uncordon <node> [<provider>]` to clear one early. | Check `cordon_details` in `lu nodes --json` and the provider's `ok` state in the gateway health feed. Clear the cordon, wait out the cooldown, restore healthy readings, or restart the controller knowing that boot recovery also moves in-flight jobs. Do not confuse a cordon with a node drain. See [operations](operations.md#provider-cordons-and-node-drains). |

> **Read and clear:** `lu nodes --json` shows active cordons in `cordon_details`; `lu uncordon`
> clears one or all of a node's cordons. Drains use `lu drain` and `lu undrain`.
